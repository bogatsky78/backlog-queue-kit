# Черга задач

Черга живе в `backlog/` і ведеться **тільки** через `bin/backlog`. Двигун —
[Backlog.md](https://github.com/MrLesk/Backlog.md), MIT, закріплений на теґу.
Клон лежить **поза репозиторієм**; у репозиторії — лише обгортка `bin/backlog`.

**Проєктні доповнення — у `.claude/queue-project.md`.** Там лежить те, чого цей
скіл знати не може: рішення власника, що ширші за одну задачу, чого в цьому
проєкті не делегують ніколи, куди йде багатослівний вивід, де живуть довгі
плани. Якщо файл є — читати його разом із цим.

## Найголовніше

**Ніколи не відкривай файли в `backlog/` через `Read`, `Grep` чи `cat`.**
Тека — це сховище CLI, а не документація. Читати треба командами:

| Що треба | Команда |
|---|---|
| що зараз у черзі | `bin/backlog task list --plain --sort ordinal` |
| план і нотатки задачі | `bin/backlog task view <id> --plain` |
| знайти задачу за словом | `bin/backlog search "<слово>" --plain` |

Це і є вся економія контексту, і вона не теоретична: список активної черги
коштує кількасот байтів, а тека задач — сотні кілобайтів. Без цього правила
агент за звичкою відкриє теку через `Read` і принесе все, що там лежить.

Правити файли `backlog/` руками не можна не з міркувань охайності: CLI
**перезаписує frontmatter із власної моделі** й мовчки викидає чужі ключі
(перевірено на v1.50.1). Тіло markdown виживає, але порядок секцій належить
CLI. Прямі правки стереже гачок `.claude/hooks/enforce-queue-cli.py` — він
відповість `deny` з підказкою, яку команду кликати замість цього.

Винятків три, і всі три — місця, де CLI просто **не має чим** писати:

- **`backlog/config.yml`** — `config set` відмовляється ставити `statuses` і
  `definition_of_done`. Пам'ятай, що CLI при кожному записі конфіга **викидає з
  нього YAML-коментарі**, тому пояснення до налаштувань лежать тут, а не там.
- **`backlog/docs/`** і **`backlog/decisions/`** — `doc create` і
  `decision create` беруть лише заголовок, прапорця на вміст немає, і жодна
  наступна команда тіла не переписує. Тобто **вміст документа й рішення
  пишеться руками, іншого шляху немає**; пошук його потім індексує. Заголовок і
  frontmatter лишає CLI, руками чіпай тіло.

Гачок ці три пропускає, решту `backlog/` — ні.

## Ситуація → команда

| Ситуація в розмові | Що робить агент |
|---|---|
| Власник згадав нову роботу, деталей немає | `bin/backlog draft create "…"` |
| Ідею обговорили, є дослідження | `doc create` + `task edit <id> --add-ref`, далі `draft promote <draft-id>` |
| Нова задача з достатнім описом | `bin/backlog task create "…" -d "…"` |
| План затверджено (вихід із plan mode) | `task edit <id> --plan "…"` плюс `--ac` на кожну перевірку |
| Почали роботу | `task edit <id> -s "In Progress"` |
| З'ясувалось щось, що переживе сесію | `task edit <id> --append-notes "…"` |
| Вийшло не так, як у плані | те саме — `--append-notes` |
| Перевірка з плану пройдена | `task edit <id> --check-ac <n>` |
| Робота закінчена | `--append-final-summary "…"`, потім `-s Done` |
| Власник сказав «прибери в історію» | `task complete <id>` |
| Задачу вирішили не робити взагалі | `task archive <id>` — **лише за словом власника** |
| Власник змінив пріоритети | `task edit <id> --ordinal <n>` |
| Власник спитав «що там у черзі» | `/queue` або `task list --plain` |
| Потрібен план або нотатки задачі | `task view <id> --plain` |
| Рішення власника, ширше за одну задачу | `bin/backlog decision create "…"` |

Команд-скорочень п'ять: `/queue`, `/queue-main`, `/queue-future`, `/queue-done`,
`/queue-history`. Їхній вивід підставляється в промпт напряму й не потребує
жодного інструмента.

## Чотири черги

| Поняття | Як виражене | Хто переводить |
|---|---|---|
| активна черга | статуси `To Do` і `In Progress` | агент |
| відкладене | статус `Later` | **лише власник** |
| ідея | чернетка, `draft create` | агент |
| зроблене | статус `Done` | той, хто закінчив |
| історія | тека `backlog/completed/`, `task complete` | **лише власник** |
| покинуте | тека `backlog/archive/`, `task archive` | **лише власник** |

Нова задача за замовчуванням іде в `To Do`. У `Later` — лише якщо власник
сказав; сама вона звідти не підіймається.

`Done` і історія — **різні речі**. `Done` лишається на дошці й видно в
`/queue-done`. `task complete` прибирає файл у `backlog/completed/`: задача
випадає зі списків і з пошуку, але лишається читабельною за ID через
`task view`. `task archive` — це не «зроблено», а «вирішили не робити»:
архівована задача зникає і зі списків, і з `task view`. CLI навмисно **не дає**
архівувати задачу в термінальному статусі — відповідає «Done tasks should be
completed, not archived».

## Порядок задач

Порядок тримає поле **`ordinal`**:

```
bin/backlog task edit TASK-12 --ordinal 20
bin/backlog task list --plain --sort ordinal
```

Номери став **розріджено** (10, 20, 30), щоб вставити щось усередину можна було
без перенумерації решти. Задачі без `ordinal` ідуть у хвіст списку.

`priority` (`High` / `Medium` / `Low`) — окрема вісь: наскільки це важливо, а не
котре за чергою. Порядок роботи визначає `ordinal`.

## ID

ID видається при створенні й **не перенумеровується**: `TASK-12` лишається
`TASK-12` назавжди, хоч куди він переїде в черзі. У прозі, в комітах і в
нотатках посилайся на ID, а не на позицію в списку — саме цим стабільний ID і
кращий за наскрізну нумерацію, яка їде разом із пріоритетами.

Два застереження:

- У чернеток **власний простір ID** — `DRAFT-1`, `DRAFT-2`. При `draft promote`
  чернетка дістає **новий** номер у просторі задач (`DRAFT-1` → `TASK-6`). ID
  чернетки тимчасовий; довговічний той, що з'явився після підвищення.
- Підзадачі **ієрархічні**: `task create -p TASK-2` дає `TASK-2.1`, `TASK-2.2` і
  так далі. Це важливо для будь-якого коду, що розбирає ID: номер не `\d+`.

## Що в яку секцію

- **Description** (`-d`) — одне-два речення. Це те, що видно в списку.
- **Implementation Plan** (`--plan`) — затверджений план, кроками.
- **Acceptance Criteria** (`--ac`) — перевірки з плану, по пунктах. Відмічаються
  через `--check-ac <n>`, а не описуються словами.
- **Implementation Notes** (`--append-notes`) — усе, що з'ясувалось під час
  роботи й переживе сесію. **Дописуємо, не переписуємо** (`--append-notes`, не
  `--notes`).
- **Final Summary** (`--append-final-summary`) — стан на кінець: що стало, чого
  не стало, що лишилось відкритим.
- **Окремий `doc`** — дослідження, розбори, довгі тексти:
  `bin/backlog doc create "…" -p research`, прив'язка до задачі через
  `task edit <id> --add-ref <шлях>` (саме `--add-ref`: голий `--ref` замінює
  весь список).
- **`decision create`** — рішення власника, ширші за одну задачу.

Машинних позначок у frontmatter не заводь — CLI їх викине. Якщо потрібна
позначка, яку видно в списку, це **label**: `task edit <id> -l "area:api"`.
Мітки приймають довільні рядки, включно з `:` і не-латиницею.

**`--add-ref` вартий окремої згадки.** Брифінг холодного агента — це
`task view <id> --plain`, і посилання в ньому єдиний спосіб сказати «довгий
план лежить там» і «робота йде в іншому репозиторії». Підзадача, яка успадкувала
посилання лише від батька, цього не покаже: `--add-ref` треба ставити **на ту
задачу, яку віддаєш**.

## `[NEEDS CLARIFICATION: …]`

Упершись у невизначеність, агент **не вгадує**. Він лишає в плані або в нотатках
машинно-помітний слід:

```
2. взяти ставку [NEEDS CLARIFICATION: з довідника чи з договору?]
```

Гачок **не пускає задачу в `In Progress`**, поки в її файлі лишились такі
маркери. Це єдине місце, де правило «агент не вгадує» перестає бути
домовленістю й стає перевіркою за ціною одного грепа. Знявши питання, заміни
маркер на те, що вирішили, — і аж тоді став статус.

## Definition of Done

`definition_of_done` у `backlog/config.yml` — гейт на правила проєкту, спільний
для всіх задач. Показується в `task view`, закривається `--check-dod`.

Окремого `constitution.md` не заводь: конституція проєкту вже є в `CLAUDE.md`
і в пам'яті, а дублікат розійшовся б з оригіналом.

## Робота з агентами

Черга робить задачу самодостатньою: брифінг для холодного агента — це
`bin/backlog task view <id> --plain` плюс `CLAUDE.md`, який вантажиться сам.

**1. Коли делегувати.** Контекст їсть **читання, а не планування**. Дослідження —
завжди агентом, і агент пише знахідки **в задачу командою**, а не переказує в
чат. Рішення власника — ніколи через агента: агент із ним не розмовляє.

**2. Проблема, що виринула всередині задачі.** Крок нульовий, до обговорення:
проблема одразу дістає свій ID (`draft create` або `task create --dep`), з
абзацом «звідки виринуло» — посилання на сесію непридатне, сесія завтра зникне.
Далі три дороги: не блокує → чернетка, не обговорюємо взагалі; блокує, бракує
фактів → агент; блокує, потрібне рішення → питаємо власника коротко, з
рекомендацією. Повернення — один рядок `--append-notes` у поточну задачу.
**Не більше одного рівня вглиб за раз.** Якщо нова проблема більша за поточну —
`--append-final-summary` фіксує, де стали, і нова задача відкривається
**окремою сесією**.

**3. Межа делегування.** Ділиться не «задача / підзадача», а **планування /
виконання**: плану немає — не делегується; план затверджений і перевірка
механічна — делегується цілком. Що не делегується ніколи: **розвилка** (агент
лишає `[NEEDS CLARIFICATION]`, пише в notes і повертається) і **звірка з
фізичним світом**. Проєктний список того, що не делегують тут, — у
`.claude/queue-project.md`.

**4. Фіналізація повертається в головний потік.** Делегована задача **не
комітить сама**. Агент доводить роботу, пише notes і final-summary, ставить
статус — і повертається. Головний потік читає **final-summary і `git diff`**, а
не подорож агента, і робить решту: коміт, push, публікацію, розгортання.

**5. Перевірка окремим агентом** — як «прогнати й відзвітувати по контрольному
списку», не як «сховати тестування». Саме там знаходиться несподіване, якого не
було в планах. Тому: **числа, а не прикметники** — агент відповідає по пунктах
`--ac`, повний вивід у файл, розходження дослівно; **хто перевіряє, той не
править** (`Bash`, `Read`, `Grep`, жодного `Edit` — інакше полагодить перевірку
замість коду); **візуальне лишається в головному потоці**; і для однієї
галасливої команди перенаправлення у файл дешевше за агента.

## Plan mode

З plan mode у чергу **можна писати**. Перевірено читанням бінарника Claude Code
2.1.232: plan mode обмежує запис рівно у двох місцях — перевірка прав на запис у
файл (`Write`/`Edit`) і гілка MCP-інструментів (`e.mcpInfo && !e.isReadOnly`).
Вбудований `Bash` не підпадає під жодну, а `Bash(bin/backlog:*)` стоїть у
`allow` — тож `task edit … --append-notes` з plan mode проходить без запиту
дозволу. Саме тому взято CLI, а не MCP-конектор, який Backlog.md теж пропонує.

Межу тримаємо свідомо: у plan mode можна **вести облік**, але не можна **міняти
проєкт**. `bin/backlog` пише лише у свою теку — це і є та межа.

## Встановлення й версія

```bash
git clone --branch v1.50.1 --depth 1 https://github.com/MrLesk/Backlog.md.git /data/backlog.md
cd /data/backlog.md && bun install --frozen-lockfile --omit=optional
```

- **З джерел, не бінарником.** `npm i -g backlog.md` тягне standalone-бінарник
  на ~101 МБ (вшитий рантайм Bun), непрозорий і неправний.
- **`--omit=optional`** пропускає шість платформних бінарників: 927 МБ → 442 МБ,
  CLI працює без них.
- **Версія закріплена.** `bin/backlog` звіряє теґ і відмовляється працювати, якщо
  клон із нього з'їхав: оновлення тихо змінює розкладку файлів під усіма
  задачами. Інший шлях до клону — змінна `BACKLOG_MD_HOME`.
- **`auto_commit: false` обов'язково.** Інакше CLI робить `git commit` сам на
  кожній зміні статусу.
- Дошка й веб-UI: `bin/backlog board`, `bin/backlog browser` (слухає лише
  `127.0.0.1`, за замовчуванням порт 6420).

Гачок після будь-якої правки — прогнати:

```bash
python3 .claude/hooks/enforce-queue-cli.test.py
```
